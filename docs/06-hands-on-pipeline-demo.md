# 6. Build, run, and inspect a pipeline yourself

This is a hands-on companion to the [pipeline concepts guide](04-pipelines.md). The earlier [PDO walkthrough](assets/pdo-ui-walkthrough.webm) shows an issue-to-code flow. Here you **create the nodes and connections**, run a read-only repository check, and open the result of every node. The two focused recordings follow those actions: [build the pipeline](assets/build-pipeline.webm) and [run and inspect it](assets/run-and-inspect-pipeline.webm).

The example asks, “Is the AI use-case value calculator ready for a five-minute internal manager demo?” Its shape is a diamond: two independent checks run at the same time, then a Claude agent combines their evidence.

~~~mermaid
flowchart LR
    S[Start] --> F[Repository facts<br/>Script]
    S --> C[Calculator checks<br/>Script]
    F -- facts --> B[Manager readiness brief<br/>Agent: Claude]
    C -- checks --> B
    B -- brief --> E[End]
~~~

The exact [pipeline YAML](examples/manager-readiness-demo.yaml) and its [three node prompts](examples/manager-readiness-demo.prompts) were copied from the PDO instance used in the videos. Their node IDs are generated by PDO; yours will differ if you build it yourself.

## Before you start

- Run the PDO daemon in Ubuntu and open [http://localhost:5172](http://localhost:5172). The status should show the daemon connected.
- Keep the cloned repository at `/home/mohamed_ballouch/test-pdo`, with the calculator on source branch `docs/pdo-onboarding`. Use your own Ubuntu path if your username differs. The branch is the work in [pull request #3](https://github.com/Mohamedballouch/test-pdo/pull/3); it contains `package.json`, `package-lock.json`, the calculator, and its tests.
- Have Node.js/npm in Ubuntu and Claude Code signed in there. See [installation](01-install-and-connect.md) and [agents and keys](02-agents-and-keys.md). This example does not need a GitHub API token: the scripts read the local Git checkout.
- On this PDO instance, `manager-readiness-demo` already exists. If you want to practice the clicks without replacing it, call your new pipeline `manager-readiness-practice`. The steps below work with either name.

A pipeline is an **instance-level reusable template**. Creating it does not bind it to GitHub or start work. You select the local repository and source branch when you create a **Run**.

## 1. Create the empty pipeline

1. In PDO, select **Pipelines** on the left, then click **+** (**New pipeline**).
2. Enter `manager-readiness-practice` on this machine, or `manager-readiness-demo` on a fresh instance, then click **Create**. PDO opens the new canvas with **Start** and **End** already present.
3. Click the empty canvas to open **Pipeline Inspector**. Keep **Prompt required** checked; this run will carry a specific question.

You do not add a separate GitHub node. **Start** holds the prompt entered at launch, while the target repository comes from the New Run form.

## 2. Choose and configure the three work nodes

Use the canvas toolbar’s **terminal icon** twice to add two **Script** nodes, then use **+ → Node** once to add an **Agent**. Select each card to edit it in **Node Inspector**. Move the cards so Start is left, the scripts are above and below each other, the Agent is to their right, and End is far right.

| Node name | Choose | Output port | Workspace | Why |
| --- | --- | --- | --- | --- |
| Repository facts | Script | Rename `out` to `facts` | Run worktree | Git metadata is deterministic; no LLM call is needed. |
| Calculator checks | Script | Rename `out` to `checks` | Run worktree | Tests and build should run as commands, not as an agent’s claim. |
| Manager readiness brief | Node (Agent) | Rename `out` to `brief` | **Run worktree** | Claude reads both reports and writes a short non-technical decision note. |

A new Agent defaults to **Isolated worktree**. Select **Run worktree** in its Workspace section to match this read-only demo. Its **Agent** selector should resolve to **claude**; the recorded pipeline uses the **Default** agent profile. Keep **Interactive** and **Orchestrator** off. Each output remains **Markdown**. The two scripts keep their default Run worktree setting.

**Why no Merge node?** Merge waits for branches that changed separate Git worktrees, then merges their code, using a resolver if necessary. These branches only produce Markdown evidence. The Agent can read the two inputs directly, so a Git merge would add work without helping this task. A Script node cannot replace the final Agent’s judgement, and the Agent should not replace deterministic test commands.

## 3. Give each node its exact job

Select **Repository facts** and paste this into **Script (bash)**. The output variable comes from its port name: `facts` becomes `$PDO_OUTPUT_FACTS`.

~~~bash
#!/usr/bin/env bash
set -euo pipefail
{
  printf '# Repository facts\n\n'
  printf 'Branch: %s\n\n' "$(git branch --show-current)"
  printf 'Latest commit: %s\n\n' "$(git log -1 --format='%h %s')"
  printf 'Tracked files: %s\n\n' "$(git ls-files | wc -l | tr -d ' ')"
  printf 'Package scripts:\n\n```json\n'
  sed -n '/"scripts": {/,/  },/p' package.json
  printf '```\n\n'
  printf 'The project includes the calculator app and its onboarding documentation.\n'
} > "$PDO_OUTPUT_FACTS"
~~~

Select **Calculator checks** and paste the next body. It installs the locked dependencies in PDO’s run worktree, then writes the real test and build output to `$PDO_OUTPUT_CHECKS`. The `nvm` line handles an Ubuntu installation where `node` is not initially on the daemon’s PATH.

~~~bash
#!/usr/bin/env bash
set -euo pipefail
if ! command -v node >/dev/null 2>&1; then . "$HOME/.nvm/nvm.sh"; fi
npm ci --prefer-offline --no-audit --no-fund >/dev/null
{
  printf '# Calculator checks\n\n'
  printf 'Node version: %s\n\n' "$(node --version)"
  printf 'Tests:\n\n```text\n'
  npm test 2>&1 | tail -n 10
  printf '```\n\nBuild:\n\n```text\n'
  npm run build 2>&1 | tail -n 10
  printf '```\n'
} > "$PDO_OUTPUT_CHECKS"
~~~

With `set -euo pipefail`, a failed `npm test` or `npm run build` makes the Script node fail even though its display captures only the last ten lines. Inspect its terminal for the full error. A Script node automatically completes on exit code 0; **do not add `pdo complete` to the Bash body**. Every declared output must exist when it exits, or PDO interrupts the node for missing output. Script nodes have a 60-second timeout, so dependency installation may need a warm cache on a slower connection.

Select **Manager readiness brief** and paste this into **Prompt**:

~~~text
Read the two upstream Markdown artifacts: repository facts and calculator checks. Write a short readiness note for a non-technical manager to the brief output path in the PDO Runtime Preamble.

Include: (1) ready/not-ready recommendation for an internal demo, (2) what the calculator helps someone decide, (3) evidence from the actual tests, build, and repository snapshot, (4) three honest caveats: illustrative assumptions, no company data, and ROI is an estimate, and (5) a five-minute demo sequence. Keep it under 350 words. If checks failed or evidence is missing, say so clearly. Do not edit source files, push to GitHub, or claim deployment. After writing the Markdown output, call pdo complete.
~~~

The Agent receives a runtime preamble naming its input and output file paths. Its own prompt states the role and evidence standard; it should write the `brief` artifact and call `pdo complete` only after the artifact exists.

## 4. Draw the five connections and save

Drag from the **border of the source card** onto the **body of the target card**. The canvas creates an input automatically; you do not manually declare inputs on the Script nodes. Draw these five edges:

1. Start → Repository facts.
2. Start → Calculator checks.
3. Repository facts (`facts`) → Manager readiness brief.
4. Calculator checks (`checks`) → Manager readiness brief.
5. Manager readiness brief (`brief`) → End (`result`).

Click an edge to see the **Edge Detail** panel. Confirm that it carries the output named in parentheses; the **Outputs** checkboxes can correct a wire if you renamed a port after drawing it. Leave **When** empty, so all five edges always fire. Both edges entering the Agent use its `in` input; its inspector pools them and names **both source nodes**. PDO waits for both checks before starting the Agent.

Click **Save** (or Ctrl+S). Reopen the pipeline from **Pipelines** to verify that the five nodes, five edges, three prompts, and port names were persisted. Saving creates the YAML and a `<pipeline>.prompts/` folder in `~/.pdo/pipelines/`; it still has not started a run.

## 5. Launch one real run

Select **Runs → New Run** and fill the form as follows:

| Field | Value used in the recorded run |
| --- | --- |
| Target repository | `/home/mohamed_ballouch/test-pdo` |
| Source branch | `docs/pdo-onboarding` |
| Pipeline | `manager-readiness-demo` (or your practice copy) |
| Sandbox | `off` for this local demo |
| Agent | Inherit/default, resolving to `claude` |
| Prompt | `Assess the AI value calculator for a five-minute internal manager demo. Use the repository facts and fresh test/build results to decide readiness. Do not change source files.` |

Click **Launch** once. PDO creates its own run branch and worktree. The two Script nodes should run in parallel; the Agent begins only when both output artifacts arrive. This is a fresh check of the code at the selected source branch, not a push or deployment.

## 6. Inspect every node and the run

Open the new row in **Runs**, then select each canvas card in turn:

1. **Start:** its Run inspector shows the exact launch prompt. This confirms what was submitted to the pipeline.
2. **Repository facts:** read the Script terminal, then click the `facts` output in **I/O → Outputs**. It records the run branch, latest commit, tracked-file count, and package scripts.
3. **Calculator checks:** read the terminal for command progress or errors. Click `checks` in **Outputs** for test totals and build result. If this node fails, the Agent should not pretend the demo is ready.
4. **Manager readiness brief:** check **I/O → Inputs**. The `in` entry pools the two source artifacts, `facts` and `checks`; open both to verify the evidence. Then open its `brief` output. The Agent’s terminal and **Initial Prompt** show how it produced the note.
5. **End:** its `result` port should say **received**. This confirms the final `brief` artifact reached the pipeline’s end.

Click **ⓘ** above the canvas for the Run’s **Info** tab: source branch, duration, number of node sessions, and estimated cost. The **Diff** tab should show no source-code changes for this read-only exercise. Inspect the Diff before archiving or cleaning up a run; archived runs may no longer preserve that Diff surface. The **YAML** tab shows the pipeline snapshot used by this particular run, which is useful if the reusable template changes later.

The completed example is run **`20261001-092822-7679785`**. PDO reports a **20-second** duration with three work-node sessions. Repository facts reported 29 tracked files. Calculator checks reported **43/43 tests passed** across two files and a successful Vite production build. Its Diff had **0 files changed**, and the final [manager brief](#the-observed-manager-brief) recommended an internal demo while naming its limitations.

### The observed manager brief

The Agent’s `brief` output says the calculator is **ready for an internal demo**, because the tests passed and the app builds. It explains that the tool helps a manager judge whether automating a repetitive task might be worth funding. It explicitly says the starting numbers are illustrative, no company systems or data are connected, and ROI/payback are estimates. Its five-minute sequence opens the local app, changes example inputs, shows the formulas, copies a summary, and ends with the caveats. The output does **not** claim deployment. Read the [exact brief generated by this run](examples/manager-readiness-brief.md).
